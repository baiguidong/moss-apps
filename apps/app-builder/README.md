# 应用构建

Create and iterate Moss Apps in an ordinary local Agent conversation. The App contributes five tools; Moss Core provides developer contracts, source snapshots, builds, isolated previews and installation receipts.

The home page follows Moss's composer and appearance settings. Start from a description, or use `@` / **选择资源** to search installed skills and assistants. Skills support multiple selection; assistants support one selection. Both controls share the selection, and drafts retain the description and selected resources across reloads. Core's `moss.apps/v1 authoring.resources` uses the same installed catalogs as new conversations; `authoring.prepare` revalidates selection and supplies the actual source directories as conversion material. No source path needs to be entered. Existing Apps are iterated from their own **迭代** action; the Builder home only offers creation and continuing its projects.

Requires Moss Host API >=3.4.0 with `moss.apps/v1` authoring methods and developer SDK export. During unpublished Host development, method availability and contract/SDK hashes identify the required snapshot.

Run `bun run check`, `bun run test`, and `bun run build` from this directory. Package with `bun run package -- --app moss.app-builder --skip-build` at the repository root. The initial package is built by CLI; an installed Builder is not required.

This workspace uses an uncommitted Core SDK/Runtime snapshot recorded in `assets/core-sdk-provenance.json`. Builds verify its SHA-256 against `vendor/moss-core`. To synchronize an intentional Core change, run `node scripts/sync-core-sdk.mjs` with `MOSS_CORE_ROOT` pointing to the source checkout, then `node scripts/generate-tool-schemas.mjs`; review the provenance and generated schema changes before building. This is a development snapshot, not a published submodule revision.

Run `test:browser`, `test:desktop`, and `test:agent` for real Electron/ordinary-Agent coverage. The Agent test requires `MOSS_BUILDER_AGENT_SETTINGS` pointing to model settings; only the text-model configuration is copied to a temporary profile. `MOSS_BUILDER_TEST_CONVERSION=1` tests local Skill input; `MOSS_BUILDER_TEST_EXTERNAL=1` tests Backend conversion and a local HTTP service with success/missing-credential/unavailable-service cases. On macOS, `MOSS_CORE_EXECUTABLE=/path/to/Moss.app/Contents/MacOS/Moss` tests a copy of the installed Core with development repository reads denied.

Sanitized local evidence is in `artifacts/moss.app-builder/verification/0.1.0/` at the repository root. Full implementation, verification limits and open acceptance items are documented in the adjacent Core repository at `ui/docs/app-builder-app-implementation.md`. Only Apple Silicon macOS has been exercised; this package has not been publicly released.

Tool scope is App-wide and selected by intended use: general helpers available in every conversation once enabled, such as Sequential Thinking, declare root-level `toolScope: "global"`; Apps requiring conversation selection use `session`, which remains the default without a cross-conversation requirement. A missing UI or navigation placement does not imply global. Ordinary edits preserve the existing scope and an omitted field means session on the current Host. Native and MCP tools inherit the same setting; global tools remain deferred unless selected and still require enablement, grants and connection. The Builder itself uses session scope and is automatically selected when the user enters its creation/edit resource. See the [App creation guide](https://github.com/baiguidong/moss/blob/main/ui/docs/app-authoring.md) for examples, compatibility and validation.

Navigation is declared by purpose at the Manifest root: `navigation: {location: "more", viewId}` for daily operations, `{location: "settings", viewId}` for configuration, or `{location: "none"}` for background/auxiliary Apps. This requires Host API >=3.4.0. Register settings through `contributes.settings` with `group` set to `integrations`, `tools`, or `apps`; operational and settings pages must have distinct routes. Use the operational, settings, or backend manifest example supplied by `builder_inspect guidance`. The generic manifest is an incomplete scaffold: choose navigation before building. Preserve existing placement in ordinary edits; validate real artifacts and restored source, not just guidance. Navigation never selects toolScope.
